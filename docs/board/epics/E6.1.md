# E6.1 - Stable contracts

## Goal

Freeze and document the surfaces that scripts and teams depend on before calling the CLI 1.0.

## Scopes (2026-10-12)

The lockfile schema, config keys (including `customAgents`), and JSON output must be documented for both scopes: project (`.hikma/lock.json`) and global (`~/.hikma/lock.json`, E4.2). Global installs must land before v1.0 so these contracts are frozen once.

## Findings from research (2026-10-17)

- **clig.dev:** keep changes additive; warn inside the program before a breaking change, name the replacement, and stop warning once the user has switched. Offer `--json` for stable machine output because human output may change. Exit zero on success, non-zero on failure, and map the main failure modes to distinct codes.
- **Peer CLIs:** Salesforce and HubSpot send deprecation notices to stderr so piped output is not broken, and vLLM names a removal version in each deprecation. Others publish a versioned output contract and promise that new fields may appear but existing fields and exit codes do not change within a major version.
- **Where Hikma stands today:** `--json` exists on three commands only (`config`, and two in `skill_install.go`). `main.go` exits with 0 or 1 only. The lockfile has `version: 1`; the config file has no version field.

## Proposed contract (pending the council run in T5)

- JSON: additive within a major version, schemas published in the docs, a `version` field in each document.
- Exit codes: 0 success, 1 failure, 2 usage error, one distinct code for `verify` mismatch so CI can tell drift from breakage. Keep the table small.
- Config and lockfile: both carry `version`; a newer file than the CLI understands is a clear error, never a silent downgrade.
- Deprecations: stderr only, one release of warning minimum, removed only in a major.

## Council run: 1.0 contract surface, 2026-10-17

Status: plan confirmed 2026-10-17. The full run on the final designs is still T5.

- Architect, `approve` with changes. A config version field is a schema change and needs a migration; the contract must say what a too-new file does. Must-fix: 1) never rewrite a newer-version file; 2) read-only commands must not migrate.
- Shipper, `trim`. Scripts and CI users are the present audience; JSON on `verify`, `list`, and `sync` has evidence of need, JSON on every command does not. Must-fix: 1) add `--json` only where a script already parses text.
- Critic, `trim`. The exit code table, the deprecation helper, and the config version are three public promises. Keep the table to four codes, and skip the helper until the first real deprecation. Worth cutting: E6.1-T7 if nothing is deprecated by 1.0.
- Terminal User, `rough`. Today every failure exits 1 and only three commands emit JSON, so scripts cannot tell failures apart. Must-fix: 1) JSON on stdout, diagnostics on stderr, always; 2) document `NO_COLOR`, `TERM`, and `--no-color` precedence together.

Decision: do T5 first, keep the exit code table to four, make T7 conditional, and limit JSON to commands scripts already read. Confidence: medium. Reopen if the first real deprecation shows the helper's shape is wrong.
