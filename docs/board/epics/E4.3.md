# E4.3 - Custom agents

## Goal

Agents are table entries in `internal/config/agents.go`. Instead of verifying and maintaining a long list of built-in agents, users define their own agent in config. Built-ins stay at the four verified agents (Claude, Codex, Copilot, OpenCode). Cursor and Gemini CLI are dropped (T1, T2): custom agents cover them. In code the concept stays `Layout` (where an agent reads skills and instructions); users only see "custom agent".

## Decided (2026-10-12)

The config key is `customAgents`. It cannot be `agents` or `agent`: those already hold plain agent names (E2.2-T7), and changing their shape would break 0.2 configs. Definition and selection stay separate: `customAgents` says what `acme` is; `agent` / `agents` / `--agent` / `HIKMA_AGENT` choose it by name.

```json
{
  "agents": ["claude", "acme"],
  "customAgents": {
    "acme": { "skillsDir": ".acme/skills", "instructionFile": "ACME.md" }
  }
}
```

## Rules

- `skillsDir` and `instructionFile` are slash-separated and relative. No `..`, no absolute paths or drive letters, and nothing inside `.git` or `.hikma` (any depth, case-insensitive).
- A custom agent name cannot reuse a built-in name. A project definition overrides a user definition with the same name.
- `skillsDir` is required; `instructionFile` is optional. `init` writes the shared AGENTS.md starter under a custom instruction file name and never overwrites without `--force` (T9).
- The project config is committed, so a definition from a cloned repo must never be able to write outside the project. The same relative paths also work under `$HOME` for global installs (E4.2), so no extra field is needed.
- `sync` must accept configured skills folders, or it would refuse every custom-agent lock entry (T5). `install --force` and `sync --force` refuse to replace an existing folder with no `SKILL.md`, so a definition like `skillsDir: "src"` can never delete project code.
- Multi-agent duplicates (T7): Copilot and OpenCode read both `.claude/skills` and `.agents/skills`, so `agents: claude,copilot` writes a skill to two folders one agent reads. The install proceeds and warns. Needs the agent list kept next to the deduplicated targets, so a blanket claude + codex warning is avoided.

## `hikma config add-agent` (T10, T11)

Editing JSON by hand works but invites typos, so a command writes the definition. `config set` cannot: the value is an object, not a string.

```
$ hikma config add-agent acme
? Skills folder (relative to the project): .acme/skills
? Save to the project config (.hikma/config.json)? [Y/n] y
? Use "acme" in this project now? [Y/n] y
Added agent "acme" to .hikma/config.json
  skills: .acme/skills
```

- Questions are y/n where possible and show the exact file. Answering n to the project file offers the user config path; n again cancels and writes nothing.
- The skills folder answer is validated as typed (same rules as on load) and re-asked on a bad value.
- No instruction-file question; `--instruction-file ACME.md` is the flag form.
- "Use it now?" adds the name to `agents` in the same file. Default yes for the project config, no for the user config (a user-level list affects every repo).
- Flags (`--skills-dir`, `--instruction-file`, `--project` or `--user`, `--use`, `--yes`) skip every prompt. Without a terminal and without the flags it refuses and names the missing one.
- It refuses built-in names and an existing definition unless `--force`, and always prints the file written.
- It never creates the skills folder. The first `skill install` does, and `init` writes the instruction file.
- `remove-agent <name>` removes the definition and, with a y/n, its entry in `agents`. `config list` shows custom agents.
- Install scope stays project-only until `--global` (E4.2); the definition is reused there rooted at `$HOME`.
