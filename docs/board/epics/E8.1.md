# E8.1: Import a skill into your registry

**Status:** active
**Assignee:** ai+verify
**Planned:** —

## Goal

Finding a skill you like and owning it takes one reviewed command: it lands in your registry with its origin recorded.

## Context

Today the path is `hikma skill install owner/repo name`, then `hikma skill push name`. That writes into the project's agent folder and lockfile first, and the pushed copy says nothing about where it came from. `gh skill` has no command for this (checked 2026-10-19: `install`, `list`, `preview`, `publish`, `search`, `update`). Plain installs are a commodity (see E3.2); the registry workflow is Hikma's job, and import is the missing step between "found it" and "it is mine".

Research that shaped the plan (first pass 2026-10-19):

- `npx skills add` and `gh skill install` both take `owner/repo`, GitHub URLs including `/tree/<ref>/<path>`, other git URLs, and local paths. `npx skills` also takes GitLab, Azure Repos and archive URLs. People paste URLs from the browser, so the parser must take them. `internal/source` does not handle tree URLs yet: they fall through to a plain git URL and the clone fails. Fixing that also gives `install` the same URLs.
- Skills are a supply-chain surface. They run with the agent's permissions, so import shows what it is about to bring in before it writes anything.
- The Agent Skills spec has optional `license` and `metadata` fields. `gh skill` records origin in `metadata.github-*` and `gh skill publish` strips those keys.
- In Go and Rust, "vendor" means a pinned copy inside your repo. Copying to edit is a different act, which is why `vendor` is not the name here.

Not in this epic: `import --update` and upstream diffs, `--all`, GitLab, Azure and archive URLs, GitHub Enterprise hosts, installing right after importing, a `--to <dir>` local write, and any search or preview (use `gh skill`).

## Review pass: principal engineer, with sources (2026-10-19)

A second review checked the plan against current primary sources. Verdict: revise. Scope and name stand; the findings below change the design and are folded into the sections that follow. Facts are marked as fetched (F) or as engineering judgment that the build must confirm with a test (J).

What the sources confirmed:

- F: `gh skill` has `install`, `list`, `preview`, `publish`, `search`, `update`, and is a public preview (needs gh 2.90+). Source: [gh manual](https://cli.github.com/manual/gh_skill).
- F: `gh skill publish` strips `metadata.github-*` and `--fix` does the same; it finds skills in `skills/*`, `skills/{scope}/*`, `*/SKILL.md` and `plugins/{scope}/skills/*`. Source: [gh publish](https://cli.github.com/manual/gh_skill_publish).
- F: `gh skill install` records source repo, ref and tree SHA in `SKILL.md` frontmatter and `gh skill update` uses it; hidden directories such as `.claude/skills/` need `--allow-hidden-dirs`; `--upstream` installs from the upstream source when a re-published skill is detected; without a name or `--all` and without a terminal it lists matches tab-separated. Sources: [gh install](https://cli.github.com/manual/gh_skill_install), [GitHub Docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills). The exact metadata key names are not in the docs; `internal/source/provenance.go` reads `github-repo`, `github-path`, `github-ref`, `github-tree-sha`, `github-pinned`, which is what to keep matching.
- F: the spec says `name` is 1-64 characters, lowercase letters, digits and single hyphens, and matches the folder; `description` is at most 1024; `license` is free text (a name or a bundled file name, not an SPDX id). Source: [Agent Skills spec](https://agentskills.io/specification).
- F: `npx skills` uses 10 MiB per download, 25 MiB extracted and 1000 files as download limits, and tries git credentials, then `gh`, then SSH for private repos. Source: [vercel-labs/skills](https://raw.githubusercontent.com/vercel-labs/skills/main/docs/commands.md).
- F: OWASP rates malicious skills Critical, says provenance proves authorship and not safety, and recommends review, scanning and hash-pinning. Source: [OWASP AST01](https://owasp.github.io/www-project-agentic-skills-top-10/ast01.html). Snyk's audit (3,984 skills; 36.82% with any flaw, 13.4% with a critical one) is a vendor report we have not checked against its data: [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub). Say "vendor report" wherever it is cited.
- F: GitHub's secondary limits allow about 80 content-creating requests a minute and 500 an hour, can change, and say to honour `retry-after` and back off. Source: [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). The Blobs docs state a 100 MB limit for reading only; do not cite a creation limit.

What changed, and why:

1. **Strip `metadata.github-*` on import (must-fix).** If upstream was installed with `gh`, its `SKILL.md` carries those keys. A byte-identical copy would carry them into the registry, and `gh skill update` or `--upstream` on a machine that installed from the registry could then fetch the upstream's current content: the reviewed copy is bypassed. `gh skill publish` strips the same keys, so there is precedent. Byte-identity therefore means "identical except `metadata.github-*` and the `--as` name line", and every such change is recorded in the origin file.
2. **Record the git tree id (must-fix).** gh tracks a tree SHA; `git rev-parse <commit>:<path>` gives the same value cheaply. It is a content-addressed pin that does not depend on Hikma's own hashing, and it is the base for a later `--update`. The per-file hashes stay because they cover the stored bytes after the strip.
3. **Read bytes from git objects, not the working tree (must-fix).** On Windows `core.autocrlf=true` rewrites line endings at checkout, and `.gitattributes` rules and Git LFS pointers can change what a working tree holds (J). That breaks "byte-identical" and the hashes. Remote sources are read with `git cat-file`/`ls-tree` at the resolved commit, with filters off. Local sources are read from the working tree, and the review says so.
4. **Import opens a pull request by default (must-fix).** *Reversed by the owner on 2026-10-20: see "Decision: import publishes like push" below.* `pushSkill` commits straight to the default branch when you can write. For third-party content that puts unreviewed code on the branch the whole team installs from, the review pass wanted import to default to a PR with `--direct` as the opt-in.
5. **Caps, rate limits, retry.** Concrete defaults, a retry on 403/429 that honours `retry-after`, and a clear message on failure (see Safety contract).
6. **Discovery is specified**, not left to the picker: the same layouts gh uses, hidden directories off by default, exact paths accepted, and a tab-separated list without a terminal.
7. **Origin file hygiene**: no credentials, no local absolute paths, commit recorded only for a clean tree.
8. **Scenarios are tested, not assumed** (table below).

## Decision: name

`hikma skill import`. It reads as "from outside, into mine", pairs with `install` (registry to agent) and `push` (local to registry), and is the word people reach for. Rejected: `fork` (implies a whole-repo fork and clashes with push's fork and PR flow), `keep` and `save` (vague, hard to search), `vendor` (jargon, and Cargo's copies are read-only), `adopt` (taken), `add` (means install in `npx skills`), `pull` and `mirror` (imply syncing), `copy` (too generic). Decided by the owner on 2026-10-19.

## The command

```bash
hikma skill import owner/repo code-review
hikma skill import https://github.com/owner/repo/tree/main/skills/code-review
hikma skill import owner/repo/skills/code-review      # an exact path skips discovery
hikma skill import owner/repo            # picker in a terminal, a tab-separated list otherwise
hikma skill import ./local/checkout my-skill
```

Flags: `--ref`, `--as <name>`, `--force`, `--pr`, `-y`/`--yes`, `--dry-run`, `--registry`, and `--json` (the plan and the result as one versioned document).

1. Resolve the source and fetch it shallow with `git` (partial and sparse for a named path in a big repo). A public upstream needs no `gh`. Branch names with slashes in a tree URL are matched against `git ls-remote`, longest first; the limit is documented.
2. Discover skills (see Discovery). Validate the chosen one with the same checks as `registry validate`.
3. Print a review: the files with sizes, the licence as written (the `license` frontmatter string and any `LICENSE*` file found, and a warning when there is neither), flags for `scripts/`, executable files, binaries, Git LFS pointers, skipped entries (symlinks, `.git`, files over a cap) and links in `SKILL.md` to paths outside the skill folder, and a prompt to read `SKILL.md` before confirming. `SKILL.md` text that tells the reader to paste or run shell commands from a URL is listed as a line to read; this is a pointer, not a scanner, and the docs say so.
4. Show the confirmation: the source and commit, the target registry and where the setting came from, and how the skill will be published, in words. Publish through the same machinery as `skill push`: a commit to the default branch when you can write, a pull request when a rule requires one or you cannot write (through your fork), and always a pull request with `--pr`.
5. Refuse to overwrite a skill the registry already has, compared case-insensitively (`Code-Review` and `code-review` collide on macOS and Windows). Show a summary of the difference; `--force` or `--as` is the way forward. With both, `--as` picks the name and `--force` allows replacing that name.
6. Write `skills/<name>/.hikma-origin.json`. Everything else is byte-identical to upstream except `metadata.github-*` (removed) and, with `--as`, the `name:` line, because the spec requires the name to match the folder. Each change is listed in the origin file.
7. End by printing the next command, such as `hikma skill install code-review`.

### Discovery

- Layouts, as `gh skill` uses them: `skills/*/SKILL.md`, `skills/{scope}/*/SKILL.md`, `*/SKILL.md`, `plugins/{scope}/skills/*/SKILL.md`, and a `SKILL.md` at the root.
- Hidden directories such as `.claude/skills/` are not searched unless the argument is an exact path to one. This matches gh and avoids importing a project's private agent setup by accident.
- An exact path (`owner/repo/skills/author/code-review`, a tree URL, or a path ending in `SKILL.md`) skips discovery.
- A namespaced skill (`skills/author/code-review`) imports under its last path segment; the full path is recorded in `path`. Two skills with the same name at different paths are listed with their paths, and the caller picks by path.
- Without a terminal and without a name, print one skill per line as `name<TAB>path<TAB>description`, then exit non-zero with "pass a name or an exact path". Never guess.
- A source that is inside the project's own agent folders (for example `.claude/skills/x`) is a local skill, not an import: suggest `hikma skill push x` and stop.

### The origin file

```json
{
  "version": 1,
  "source": "owner/repo",
  "ref": "main",
  "commit": "<full sha>",
  "tree": "<git tree id of the skill folder at that commit>",
  "path": "skills/code-review",
  "license": "MIT",
  "files": { "SKILL.md": "sha256:..." },
  "changes": [
    { "file": "SKILL.md", "reason": "strip-github-metadata", "upstream": "sha256:..." }
  ]
}
```

- `source` is normalized and credential-free: `owner/repo`, or the URL with any user, token or query removed. A local path is recorded as `local`, never as an absolute path. `ref` is the requested ref or null.
- `commit` and `tree` are recorded only when the source is a remote checkout or a clean local git tree. A dirty or non-git local source records `null` for both, and the review says why. The file hashes are the truth in that case.
- `files` hashes the stored bytes. `changes` lists every difference from upstream, with the upstream hash, so a reader can tell edited-by-import from edited-later.
- `license` is the raw string from upstream, or null. It is not parsed as SPDX; the spec does not require it.
- A new public format inside registries: a `version` field and a tolerant reader from the first release, documented in the policy page. A hash mismatch after someone edits the skill later is normal. `registry validate` checks the schema and containment of `path`, never the hashes, and `skill info` may show "edited since import".
- It is advisory. It records where a copy came from; it does not prove the copy is safe.

It is a sidecar and not `metadata.github-*` in `SKILL.md`, because editing `SKILL.md` would break byte-identity with upstream, `gh skill publish` strips those keys, and a stale key could make `hikma skill adopt` or `gh skill update` pull from upstream instead of your registry. The hashes and the tree id also give a later `--update` its base for a three-way comparison.

### Safety contract

- Everything read from the upstream skill is untrusted: names are one path segment, paths stay inside the skill folder, symlinks and `.git` are skipped and reported, and there are caps. Default caps: 100 files and 5 MiB in total, documented, with no override flag in the first release. For comparison, `npx skills` allows 25 MiB and 1000 files.
- File bytes come from git objects with filters off, so line endings, `.gitattributes` and LFS pointers cannot change them. An LFS pointer is flagged and the import refuses, because the file would be unusable.
- The write goes to the registry through the gated push flow: the user sees the target and confirms, and `--yes` is the only way to skip the question. It never comes from config or an environment variable. `--yes` skips the question and nothing else; the line that says how the skill is published is still printed.
- Nothing prompts without a terminal: print the plan and exit, `--yes` to proceed. All validation and the review happen before the first network write.
- A missing licence is a warning shown in the review and the confirmation. `--yes` accepts it, in line with "`--yes` is the only way to skip the question", and the plan is always available first with `--dry-run`.
- Executable bits come from git's file mode, not the filesystem, so they survive Windows. Registry paths use forward slashes.
- Progress goes to stderr and the result to stdout; a missing or signed-out `gh` gets a message that names the next command.
- Calls to the GitHub API retry on a 403 or 429, wait for `retry-after` (else at least a minute), back off, and stop after a fixed number of tries with a message that says how many files were uploaded and that nothing was committed. GitHub allows about 80 content-creating requests a minute and 500 an hour; at the file cap an import fits. This retry is added to the shared push path, so `skill push` gets it too.
- Never overwrite silently: neither an existing registry skill nor anything local.

## Decision: import publishes like push (owner, 2026-10-20)

Import follows the tool: it does what `skill push` does, so the registry behaves one way. With write access and no rule requiring pull requests it commits to the default branch, whatever that is called; when a rule requires pull requests, or you cannot write, it opens a pull request (through your fork without write access); `--pr` always opens one. `--direct` is gone, and it was never released.

This reverses the review pass's must-fix that import default to a pull request. The reasons it is acceptable: the registry is the user's own, the review and the confirmation come first and the confirmation says "with no review" in words, and a registry that wants review can require it with a branch rule or ruleset, which hikma sees and follows. What stays open: `--yes` in CI puts third-party content on the branch a team installs from when nothing requires review. The docs say so and tell scripts to pass `--pr`. Reopen if someone publishes unreviewed third-party code by accident, or if classic branch protection (not visible to the rules endpoint) catches people out.

**init and doctor report the mode and store nothing.** A registry's publishing mode is a fact GitHub knows (default branch, whether pull requests are required) combined with a fact about the person (write access). Saving it in config would go stale, would be wrong for a teammate with different access, and in committed project config would let a repository file decide whether a skill goes straight to the default branch, which breaks "committed config is untrusted". So `init` and `doctor` ask GitHub, print one line (what publishing will do, and why), and ask nothing; they stay silent without `gh`, a sign-in, a `--dry-run`, or a registry outside GitHub. A user-level "always use a pull request" key was considered and left out: it has one caller, and `--pr` or a branch rule already covers it. New config keys are public contracts since 1.0.

Built as `registryAccess` (default branch, can write, requires pull requests), used by the confirmation text in `push` and `import`, by `init`, and by `doctor`. `pushSkill` still makes its own calls and was not changed.

## Built (2026-10-19)

Where the build differs from the plan above, and why:

- **Rate-limit retry waits a fixed one, two, then four minutes.** `gh api` does not show the `Retry-After` header, so it cannot be honoured; the waits follow GitHub's advice for secondary limits. The retry sits in `ghGet` and `ghSend`, so `skill push` gets it too. A failed upload says how many files went up and that nothing was committed.
- **`--dry-run` never contacts GitHub**, so it cannot check for a name collision. It says so, and works without a configured registry. A real import resolves the registry first, before it downloads anything.
- **`install` takes a folder or tree URL only where `Discover` can find the skill** (`skills/<name>/`, `<name>/`, the root). The lockfile has no path field, so a skill in another layout could not be updated later; the error points at `skill import`, which finds more layouts.
- **Overwrite removes stale files.** With `--force`, `pushSkill` lists the registry's existing copy and deletes files the new one does not have (`replace` on the push plan). A name that differs only in letter case is refused even with `--force`.
- **Remote sources are fetched with `--filter=blob:none --no-checkout`** and read with `git ls-tree` and `git cat-file`, with a fallback to fetching a commit id and to `gh repo clone`. A local folder is read from the working tree, and the review says so.
- **The progress line (`Reading ...`) goes to stderr always**, so the tab-separated skill list on stdout is clean.
- **Tests**: source parser table, git-object reads with `core.autocrlf=true` and a `.gitattributes` that rewrites text, caps, LFS, case collisions, metadata stripping, the command against a fake GitHub (a direct commit, a pull request with `--pr` and when a rule requires one, through a fork, another default branch name, refusal, force with stale files, `--as`, no terminal, JSON), a GitHub source read through git's URL rewriting, and `install` with the new forms. The real round trip (`e2e/github_test.go`) now imports a skill back into the throwaway registry; it needs a token and was not run yet.
- Checked against real GitHub on 2026-10-19: `hikma skill import https://github.com/anthropics/skills/tree/main/skills/pdf --dry-run` reads 12 files from git objects at the commit and shows the licence line (`Proprietary. LICENSE.txt has complete terms`).

## Exit
