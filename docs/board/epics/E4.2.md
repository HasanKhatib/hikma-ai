# E4.2 - User-scope installs

## Goal

Let users install skills into their home directory (`--global`) with the same lockfile, verify, and safety gates as project installs. Un-parked 2026-10-12 (it was parked on 2026-10-10 because `gh skill --scope user` covers installs; hikma adds the lockfile, verify, sync, and script-change confirmation for personal skills).

## Design (decided 2026-10-12)

- **Scope is a root.** Project scope is `.` with `.hikma/lock.json`. Global scope is `$HOME` with `~/.hikma/lock.json`. The agent folders (built-in and custom agents) are reused unchanged: every built-in layout folder (`.claude/skills`, `.agents/skills`) is valid relative to `$HOME`, so no new layout field is needed and lockfile keys stay relative and portable.
- **Explicit only.** `--global` / `-g` on the command. It cannot come from config or an environment variable, so a cloned repo can never trigger a global write.
- **Commands.** install, update, remove, adopt, list --installed, verify, diff, sync. `init` stays project-only. Works outside a git repo.
- **Confirmation.** A global write prints the absolute target and asks (`--yes` for scripts). Script changes keep their existing confirmation.
- **Symlinks.** Refuse to write through a symlinked target (people link global skills to their own dev repos). Detect a shared folder reached through a symlink so a skill is not installed twice.
- **Portability.** `~/.hikma/lock.json` is a plain dotfile; chezmoi, stow, or a dotfiles repo can carry it. `hikma sync --global` then restores after a wipe. It is documented as a restore tool, not a headline feature.
- **Duplicates warn, never block.** A skill name present at both scopes warns on install, in `list`, and in `doctor`.
- **Sync safety.** A project lockfile entry that shares a name with an installed global skill is called out before restoring.

## Where agents read personal skills (verified 2026-10-12)

| Agent | Global folder | Source |
| --- | --- | --- |
| Claude Code | `~/.claude/skills` | https://code.claude.com/docs/en/skills |
| Codex | `$HOME/.agents/skills` | https://learn.chatgpt.com/docs/build-skills |
| Copilot | `~/.agents/skills` (also `~/.copilot/skills`, but see below) | https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills |
| OpenCode | `~/.agents/skills` (also `~/.config/opencode/skills` and `~/.claude/skills`) | https://opencode.ai/docs/skills |

Copilot: a reported bug says skills in `~/.copilot/skills` were not discovered (github/copilot-cli#4545), so hikma uses `~/.agents/skills`.

## Same name at both scopes: what is known

- **Claude Code:** documented, and confirmed on 2.1.235: both copies are listed (tagged user and project), and the slash command runs the personal (global) copy. Workaround: rename one. Not verified: which copy the model loads on its own.
- **Codex:** both copies are listed, no documented winner (openai/codex#9930; project-first is an open request, #25324).
- **OpenCode:** the winner is non-deterministic, last file read wins (anomalyco/opencode#53119). Skill permission rules are bound to the name.
- **Copilot:** not documented; third-party guides say project wins. Use `/skills info NAME` to check.

Do not document a winner as fact for anything but Claude Code. E4.2-T9 records what each agent actually does, by hand.

## Risks

- Tests that touch the real home directory (T8 exists to prevent it).
- Precedence differs by agent and is mostly undocumented.
- Claude personal skills do not load in cloud or Cowork sessions, so global installs do not help in a Codespace.
- Must land before v1.0, which freezes the lockfile and config contracts.
