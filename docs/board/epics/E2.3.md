# E2.3 - Skill lifecycle for public users

## Goal

Make skill list, install, create, update, and publish flows work with arbitrary registries.

## Product Behavior

Hikma AI should help users maintain their own reusable skill registry instead of relying on one centrally owned registry. The CLI should make the registry structure understandable and should fail loudly when a registry is missing required files.

## MVP Commands To Evaluate

- `hikma skill list`
- `hikma skill install <name>`
- `hikma skill create <name>`
- `hikma skill update <name>`
- `hikma registry get`
- `hikma registry set <url>`

## Exit Check

Skill lifecycle commands are documented, tested, and independent of any fixed registry owner.

## Review Additions

- Public registries are read with `git clone --depth 1` or HTTPS; `gh` is needed only for `push` and private registries.
- Registry values may be GitHub shorthand, any git URL, or a local path (also the basis for fixture tests).
- Registry spec is documented; `hikma registry validate` checks it. `list` falls back to scanning `skills/*/SKILL.md` when there is no index.
- `.hikma/lock.json` records registry, commit, and version per installed skill.

## Design Decisions (2026-10-01)

- Install from any repo: `hikma skill install <owner/repo> <name>`. Bare `hikma skill install <name>` uses the configured registry. `owner/repo` with no name opens a picker; non-interactive runs list skills and exit. `--ref` pins a tag, branch, or commit.
- Install enforces no naming convention, only path safety (single path segment inside the skills directory).
- Push always goes to the configured registry and is gated: show the registry and where it came from, ask for confirmation, `--yes` for scripts. Use fork and PR when there is no write access; never force-push; CODEOWNERS edits are opt-in.
- The lockfile records the source repo and commit per skill, so update works across many sources.
- Skills are discovered by directory scan; an index file is optional.

## Push and Validation (2026-10-09)

- `hikma registry validate [source]` checks each skill: frontmatter `name` matches the folder, `description` present, naming setting respected, no placeholders. `push` runs the same checks first.
- `push` detects write access. Without it, it forks, syncs the fork, pushes there, and opens the PR across forks.
- No force-push: an open PR gets a new commit on its branch; a leftover branch without an open PR is never rewritten, a new timestamped branch is used.
- Binary-safe blobs, executable bit preserved, and a "no changes" short-circuit.
- All `gh` calls go through one seam (`ghRun`) so the flows are tested with a fake.
