# E7.1 - Agent working model

## Goal

Write down how Claude works in this repo so the rules do not live only in chat: who pushes, what a commit may carry, and how contested decisions get reviewed before they are built.

## Context

Borrowed in spirit from a sibling project that runs a four-seat "council" before consequential changes. Adapted here: four seats, advisory only, one of them a terminal user who works across macOS, Linux, and Windows and scripts the CLI.

Shipped in the menu PR (#37), merged 2026-10-17:

- `AGENTS.md` "Git and Pushing": push and run `gh` writes as the logged-in `gh` user, never switch accounts or override git identity, no co-author or generated-by lines, squash merges copy trailers so check before merging.
- `AGENTS.md` "Council" and `.claude/skills/council/`: Architect (integrity, trust boundaries), Shipper (value, momentum), Critic (simplicity and maintenance cost, which also covers what a separate steward seat would), Terminal User (platforms, scripts, CI, no-TTY).
- `AGENTS.md` "CLI Interaction Rules": flags are the API, no prompts without a TTY, confirm before writing, prompts behind `Prompter`, color only on a terminal, cross-platform behavior.
- Non-Goals: "No full-screen TUI" replaces "no TUI", so a prompt-driven menu is in scope.

## Rules

- The council is advisory. It never edits files or runs commands, and nothing follows a run until the human confirms.
- Keep it at four seats. A missing lens folds into the closest seat.
- Accepted decisions are recorded as a note on the board task they affect, not in the skill.

## Council run: wizard flow (E7.3), 2026-10-17

Status: confirmed by the human on 2026-10-17.

Question: how should the wizard and prompts be built out (T5 to T10) before v0.5, and should the menu loop?

Seats:

- Architect, `approve` with changes. Findings: the menu already runs the same command code and keeps each command's own confirmation, which is the right trust boundary. Menu input becomes command arguments, so T6 values need the same validation as `askName` (non-empty, one word, no leading dash). Swapping the prompt library must not change which confirmations exist. Must-fix: 1) T6 collects only validated values and never builds a path or shell string; 2) every existing confirmation (`push`, `sync`, global `Continue?`, `update` scripts) keeps its default of No.
- Shipper, `trim`. Findings: T10 is small and unblocks CI users now. T5 is invisible to users but is the prerequisite for T9. T7 has no evidence anyone wants it and a looping menu fights scripting. Must-fix: 1) defer T7; 2) do not hold v0.5 for T6 pickers beyond install and publish.
- Critic, `trim`. Findings: `Prompter` needs `Confirm` and `MultiSelect` to cover T5; adding methods is fine, adding a second abstraction is not. Do T5 on survey first, then T9 as a one-file swap, so a regression has one cause. `--no-input` and `--no-color` are public flags that must hold after 1.0. Worth cutting: the direct `survey.AskOne` calls once T5 lands, and the survey dependency after T9.
- Terminal User, `rough`. Findings: `--no-input` must fail naming the flag to pass, with a non-zero exit and the message on stderr. `--no-color` must match `NO_COLOR`, and neither flag may print decoration to stdout. huh is unchecked on PowerShell and the legacy console, and Ctrl-C must stay quiet. Must-fix: 1) T9 keeps survey until huh passes a Windows hand walk (accessible mode too); 2) each menu entry prints its equivalent command, including values collected in T6.

## Decision

Build in this order: T10, T5 (still on survey), T9 (one-file swap behind `Prompter`, gated on a Windows check), T6 (install and publish first), then the hand walks (T8, E7.2-T5). Defer T7: the menu exits after one task so a run stays scriptable.

## Confidence

Medium. The order is low risk. The huh swap depends on Windows behavior nobody has checked.

## Dissent

None overridden. The Terminal User's `rough` verdict is a condition on T9, not a blocker.

## Reopen if

huh fails on Windows PowerShell or the legacy console, users ask for a looping menu, or `--no-input` turns out to need per-command behavior.
